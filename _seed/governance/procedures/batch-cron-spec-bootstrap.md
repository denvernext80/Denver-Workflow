프로젝트에 **배치·크론 명세 인덱스가 아직 없을 때 딱 한 번** 도는 절차다. 정기 실행되는 작업
(전문용어: 배치=모아서 한 번에 처리하는 작업, 크론=정해진 시각에 자동 실행되는 작업)을 전부
찾아 vault `project/reference/` 에 명세 3종을 세운다. 이후 갱신은 [[batch-cron-spec-update]] 가 맡는다.

**언제 쓰나:** `/dw-setup` 4단계 직후, 또는 `dw_search("배치 크론 명세 전체 인덱스")` 가 0건일 때.

## 0. 멱등 확인 (먼저 한다)

인덱스가 이미 있으면 **이 절차를 자동으로 돌리지 않는다** — 사용자에게 "배치·크론 명세가 이미
있습니다. 지금 다시 훑을까요?" 라고 묻고, 동의가 있을 때만 진행한다. 말없이 덮어쓰지 않는다.

## 1. 표면 전수 탐색 — 여기가 이 절차의 핵심

API 와 달리 **정본이 한 곳에 없다.** 정기 실행은 여러 표면에 흩어져 선언되고, 그중 일부는
**레포 안에 아예 없다**. 아래를 **전부** 훑는다. 하나라도 건너뛰면 "아무도 모르는 잡"이 남는다.

**A. 레포에 선언된 것 (읽을 수 있다)**
- CI 서비스의 스케줄 트리거 (워크플로우 정의의 `schedule`/`cron` 키)
- 서비스 매니저의 타이머 유닛 (`*.timer` + 짝이 되는 `*.service`)
- 컨테이너/오케스트레이터의 정기 실행 정의 (예약 잡·크론 잡 리소스)
- 애플리케이션 프레임워크 내장 스케줄러 (코드에 등록된 주기 작업)
- 크론 항목을 **설치하는 스크립트** — 배포·프로비저닝 스크립트가 `crontab` 을 심는 경우가 흔하다.
  이건 "레포에 있지만 실제 등록은 호스트에서 일어나는" 경계 사례다. **레포 선언분으로 세되
  호스트 확인 대상으로도 표시한다.**
- 크론식이 하드코딩된 셸/설정 파일 (`*/5 * * * *` 같은 패턴 grep)

**B. 호스트에 설치된 것 (못 읽을 수 있다)**
- 실행 호스트의 사용자·시스템 크론 목록
- 서비스 매니저에 등록됐지만 레포에 유닛 파일이 없는 타이머
- 클라우드 스케줄러 콘솔에만 존재하는 정기 실행

**B 를 확인할 수 없으면 추측하지 말고 `미확인` 으로 남긴다.** 운영 접근이 상시 열려 있지 않은
환경이 정상이다(접근 제한·한시 개방). **접근을 얻으려고 보안 설정을 바꾸지 않는다.**
인덱스에 `호스트 설치분: 미확인 (최종 확인 YYYY-MM-DD, 사유)` 로 적고 넘어간다 —
**모른다고 적는 것이, 없다고 적는 것보다 정확하다.**

## 2. 전수 열거와 총계

표면별로 센다. **레포 선언분과 호스트 설치분을 절대 한 숫자로 합치지 않는다** — 확인 수준이
다른 둘을 합치면 "다 안다"는 착각이 생긴다.

## 3. 잡 1건에 기록할 것

| 필드 | 설명 |
|---|---|
| 이름 | 사람이 부르는 이름 |
| **선언 표면** | 위 1번의 어디에 선언됐나 (파일 경로 또는 "호스트 설치") |
| **스케줄 + 타임존** | 크론식/주기 + **어느 시간대 기준인가**. 타임존 누락이 가장 흔한 사고다 |
| 실행 호스트 | 어디서 도나 |
| 실행 대상 | 실제로 무엇을 실행하나 (명령·스크립트·엔드포인트) |
| **상태** | `활성` / `비활성`(꺼져 있음) / `보류`. **꺼진 잡도 반드시 기록한다** — "왜 꺼졌나"가 나중에 가장 궁금해지는 정보다 |
| 중복 실행 정책 | 이전 실행이 안 끝났으면 어떻게 되나 (겹침 허용/스킵/잠금) |
| 타임아웃 | 있으면 값, 없으면 "없음"이라고 명시 |
| 실패 시 | 알림이 가나, 재시도하나, 조용히 죽나. **"조용히 죽음"도 기록할 상태다** |
| 최종 실측 확인일 | 이 항목을 실제로 확인한 날 |

## 4. 그룹 분할

목적(정리·동기·리포트·헬스체크)이나 실행 호스트로 묶는다. 잡이 15건 이하면 나누지 말고
인덱스 한 장에 다 넣는다. 작은 프로젝트에 문서 여러 장은 과잉이다.

## 5. 기록 (그룹 → 인덱스 → 이력 순서)

`dw_write_reference(scope, title, body, source)` 로 기록한다.

1. **그룹마다** (분할했다면): title `배치·크론 명세 — <그룹 이름>`. 3번 필드를 잡마다.
2. **인덱스 하나**: title `배치·크론 명세 — 전체 인덱스`. 담을 것 —
   공통 규약(기본 타임존·알림 채널·재시도 관례·잠금 방식) / **표면별 잡 수 표(레포 선언분 ·
   호스트 설치분 분리)** / 그룹별 상세 노트 파일명 / 총계 /
   **호스트 설치분 확인 상태**(확인함 또는 `미확인 (최종 확인 YYYY-MM-DD, 사유)`) / 재대조 날짜.
3. **이력 하나**: title `배치·크론 명세 — 변경 이력`. 부트스트랩 항목으로 시작:
   `- **YYYY-MM-DD** · 부트스트랩 · 전 표면 탐색 — 레포 선언 N개 / 호스트 설치 M개(또는 미확인). 근거: <커밋 SHA>`

## 6. 정기 실행이 하나도 없을 때

**빈 인덱스와 빈 이력을 만든다.** "없다" 와 "비어 있다" 는 다르다 — 후자여야 첫 배치를 만들 때
[[batch-cron-spec-update]] 가 갱신할 대상을 찾는다.
- 인덱스 body: "이 프로젝트에는 현재 정기 실행 작업이 없다. 첫 배치/크론이 생기면
  batch-cron-spec-update 절차로 이 문서를 채운다." + 공통 규약 자리(제목만).
- 이력 body: `- **YYYY-MM-DD** · 부트스트랩 · 정기 실행 없음 — 빈 명세 생성.`

## 7. 검증

- `dw_list(note_type="reference")` 에 인덱스·이력(+그룹들)이 보인다.
- 인덱스의 표면별 합계 = 2번에서 센 총계.
- 호스트 설치분이 `미확인` 이면 **사유와 최종 확인일이 반드시 적혀 있다**(빈 미확인 금지).

**주의:**
- **비활성 잡을 "없는 것"으로 처리하지 마라.** 꺼진 스케줄은 삭제된 스케줄이 아니다.
- 호스트를 못 봤으면서 "전수 파악 완료"라고 쓰지 마라. 이 도메인의 가장 큰 사고는 틀린 명세가
  아니라 **아무도 모르는 채 도는 잡**이고, 그건 `미확인` 표기가 있어야 나중에 찾아진다.
- 멀티레포·다중 호스트면 레포/호스트마다 따로 세고 인덱스에 나눠 적는다.
