정기 실행 작업(배치·크론)이 바뀌었을 때 vault 명세를 따라 맞추는 절차다. 최초 생성은
[[batch-cron-spec-bootstrap]] 이 맡는다.

**언제 쓰나:** 잡을 새로 만들었거나, 스케줄·실행 대상·타임아웃·알림을 바꿨거나, 껐거나, 없앴을 때.
**적용 시점 기준이 API 명세와 다르다** — 코드 머지가 아니라 **실제로 그 스케줄이 도는 상태가 된
시점**이다. 레포에 선언만 하고 배포/설치를 안 했으면 아직 현재 상태가 아니다.

## 1. 델타 확정

넷 중 하나로 분류한다:

- **신규** — 없던 정기 실행이 생겼다.
- **변경** — 스케줄식·타임존·실행 대상·타임아웃·중복 정책·알림이 달라졌다.
- **비활성** — 잡은 남아 있는데 껐다. **삭제가 아니다.** 상태만 `비활성` 으로 바꾸고 왜 껐는지 적는다.
- **삭제** — 선언과 등록을 모두 제거했다.

대상이 아닌 것: 잡이 실행하는 스크립트 **내부** 로직만 바뀐 경우(스케줄·인터페이스가 그대로면
명세는 그대로다). 판정 기준은 **"언제·어디서·무엇이 도는지"가 달라졌는가**.

## 2. 그룹 상세 노트 갱신

바뀐 잡이 속한 그룹 노트 **하나만** 연다(`dw_read`). 부트스트랩 절차 3번의 필드를 그대로 유지한다.
**최종 실측 확인일을 오늘로 갱신한다** — 이 날짜가 없으면 명세를 믿을 수 없다.

## 3. 인덱스 갱신

- 표면별 잡 수와 총계를 다시 센다. **레포 선언분과 호스트 설치분은 계속 분리해서** 센다.
- 공통 규약(기본 타임존·알림 채널 등)이 바뀌었으면 그 섹션도 고친다.
- 호스트 설치분을 이번에 실제로 확인했으면 `미확인` 을 걷고 확인일을 적는다. 못 봤으면
  **이전 `미확인` 표기를 그대로 둔다** — 확인하지 않은 것을 확인한 것처럼 바꾸지 않는다.

## 4. 변경 이력 prepend (이 단계를 건너뛰면 갱신이 아니다)

`배치·크론 명세 — 변경 이력` 을 `dw_read` 로 읽고 **맨 위에** 항목을 붙인 뒤 전체를
`dw_write_reference` 로 다시 쓴다(같은 title 은 덮어써지므로 읽은 내용을 통째로 되돌려 써야
기존 이력이 보존된다 — **읽지 않고 쓰면 이력 전체가 날아간다**).

항목 형식:

    - **2026-07-27** · 신규 · `nightly-cleanup` (매일 03:00 KST, 호스트 설치) — 한 줄 요약. 근거: PR #123 (`abc1234`).

- 날짜는 **실제로 돌기 시작한 날**(배포·설치일). 유형은 신규/변경/비활성/삭제/재대조.
- 변경이면 **무엇이 무엇으로** 바뀌었는지 적는다("매시 → 매일 03:00", "타임아웃 없음 → 10분").
- **비활성·삭제 사유를 반드시 적는다.** 이 도메인에서 가장 자주 묻는 질문이 "이거 왜 꺼져 있죠?"다.
- 삭제된 잡은 그룹 노트에서 사라지지만 **이력에는 영구히 남는다.**

## 5. 검증

- 인덱스 총계 = 그룹 노트들의 잡 수 합계(레포 선언분·호스트 설치분 각각).
- 이력 맨 위가 이번 변경이고 그 아래로 기존 이력이 **전부** 남아 있다(줄 수가 줄면 사고다).
- 비활성으로 바꿨다면 그룹 노트의 상태 필드와 이력 항목이 서로 맞는다.

**주의 — 드리프트 판정이 API 명세와 반대인 경우가 있다:**

- **레포 선언분**: 명세와 코드가 다르면 **코드가 이긴다.** 명세를 고치고 이력에 "변경"으로 남긴다.
- **호스트 설치분**: 명세와 호스트가 다르면 **자동으로 명세를 맞추지 마라.** 누군가 수동으로
  심었거나 지웠을 수 있다 — 의도된 변경인지 사고인지 사람만 판단할 수 있다.
  **불일치 사실을 사용자에게 보고하고 판단을 받은 뒤에** 명세를 고친다.
  조용히 명세를 호스트에 맞추면 무단 변경이 정본으로 승격된다.

그 밖에:
- 여러 잡을 한 번에 바꿨으면 이력 항목도 그만큼 쓴다.
- 스케줄을 바꿀 땐 타임존을 함께 확인한다 — 서버 시간대와 표기 시간대가 다른 사고가 흔하다.
