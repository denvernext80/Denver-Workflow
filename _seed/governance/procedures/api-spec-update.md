API 표면(전문용어: 바깥에서 호출할 수 있는 HTTP 엔드포인트 전체)이 바뀌었을 때 vault 명세를
따라 맞추는 절차다. 최초 생성은 [[api-spec-bootstrap]] 이 맡는다.

**언제 쓰나:** 엔드포인트를 새로 만들었거나, 요청/응답/인증을 바꿨거나, 없앴을 때. 머지 직후
(PR 이 main 에 들어간 뒤)가 기본 시점이다 — 머지되지 않은 것은 아직 "현재 상태" 가 아니다.

## 1. 델타 확정

이번 변경이 API 표면을 어떻게 바꿨는지 한 줄로 확정한다. **셋 중 하나로 분류한다:**

- **신규** — 없던 엔드포인트가 생겼다.
- **변경** — 경로/메서드는 그대로인데 요청 파라미터·응답 shape·인증·에러가 달라졌다.
- **삭제** — 엔드포인트가 없어졌다.

대상이 아닌 것: 내부 함수 시그니처 변경, 리팩터링, 응답에 영향 없는 성능 개선.
**판정 기준은 하나다 — 호출하는 쪽이 관측할 수 있는 변화인가.**

## 2. 도메인 상세 노트 갱신

바뀐 엔드포인트가 속한 도메인 노트 **하나만** 연다(`dw_read`). 다른 도메인은 건드리지 않는다.

- 신규: 해당 섹션에 엔드포인트 항목을 추가한다(다른 항목과 같은 형식으로).
- 변경: 해당 항목의 바뀐 줄만 고친다.
- 삭제: 해당 항목을 지운다.
- 문서 맨 위 실측 기준 커밋 SHA 를 이번 커밋으로 갱신한다.

`dw_write_reference` 로 같은 title 에 재기록하면 덮어써진다.

## 3. 인덱스 갱신

`API 명세 — 전체 인덱스` 를 읽고 고친다:
- 해당 도메인의 엔드포인트 수와 총계를 다시 센다(신규 +1 / 삭제 -1 / 변경 ±0).
- 공통 규약이 바뀌었으면(새 인증 방식, 에러 포맷 변경 등) 그 섹션도 고친다.
- 재대조 날짜와 실측 기준 커밋을 갱신한다.

**숫자를 눈대중으로 고치지 않는다** — 도메인 노트의 항목 수를 실제로 세서 맞춘다.

## 4. 변경 이력 prepend (이 단계를 건너뛰면 갱신이 아니다)

`API 명세 — 변경 이력` 을 `dw_read` 로 읽고, **맨 위에** 항목을 한 줄 붙인 뒤 전체를
`dw_write_reference` 로 다시 쓴다(도구가 같은 title 을 덮어쓰므로 읽은 내용을 통째로 되돌려 써야
기존 이력이 보존된다 — **읽지 않고 쓰면 전체 이력이 날아간다**).

항목 형식:

    - **2026-07-27** · 신규 · `POST /api/v1/foo/bar` — 한 줄 요약. 근거: PR #123 (`abc1234`). 계약: [[계약노트명]]

- 날짜는 머지된 날. 유형은 신규/변경/삭제/재대조 중 하나.
- 요약은 "무엇이 어떻게" — 변경이면 무엇이 어떻게 달라졌는지 적는다("응답에 `x` 필드 추가",
  "익명 허용 → Bearer 필수").
- 근거는 PR 번호 + 커밋 SHA. 계약 노트가 있으면 링크하고, 없으면 그 부분을 생략한다.
- **삭제된 엔드포인트는 도메인 노트에서 사라지지만 이력에는 영구히 남는다.** "왜 이 API 가
  없어졌나" 에 답할 수 있는 유일한 기록이라, 이력에서 지우는 일은 없다.
- 이력이 길어지면 연도 heading 으로 접는다. 노트를 쪼개지는 않는다 — 한 시계열인 것이 검색 가치다.

## 5. 검증

- 인덱스 총계 = 도메인 노트들의 항목 수 합계.
- 이력 맨 위 항목이 이번 변경이고, 그 아래로 기존 이력이 **전부** 남아 있다(줄 수가 이전보다 줄면 사고다).
- 계약 노트가 있었다면 `dw_resolve` 로 archive 한다 — 내용이 명세로 흡수됐으므로 계약의 역할은 끝났다.

**주의:**
- 명세와 코드가 어긋나면 **코드가 이긴다.** 명세를 코드에 맞추고 이력에 "변경" 으로 남긴다.
  코드를 명세에 맞추라는 뜻이 아니다.
- 여러 엔드포인트를 한 PR 에서 바꿨으면 이력 항목도 그만큼 쓴다. 한 줄로 뭉뚱그리지 않는다.
- 머지 전(리뷰 중)에 명세를 미리 고치지 않는다 — 명세는 "현재 상태" 이지 "계획" 이 아니다.
  계획은 vault `contracts/` 의 몫이다.
