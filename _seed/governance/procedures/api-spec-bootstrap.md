프로젝트에 **API 명세 인덱스가 아직 없을 때 딱 한 번** 도는 절차다. 기존 코드의 API 를 전수로
훑어 vault `project/reference/` 에 명세 3종을 세운다. 이후 갱신은 [[api-spec-update]] 가 맡는다.

**언제 쓰나:** `/dw-setup` 4단계 직후, 또는 `dw_search("API 명세 전체 인덱스")` 가 0건일 때.

## 0. 멱등 확인 (먼저 한다)

`dw_search("API 명세 전체 인덱스")` 로 인덱스 존재를 확인한다. **이미 있으면 이 절차를 자동으로
돌리지 않는다** — 사용자에게 "API 명세가 이미 있습니다. 지금 다시 훑어서 갱신할까요?" 라고 묻고,
동의가 있을 때만 진행한다. 기존 명세를 말없이 덮어쓰지 않는다.

## 1. 케이스 판별

- **케이스 A — 이 프로젝트가 HTTP API 를 제공한다**: 2번으로.
- **케이스 B — API 가 없다(프론트 전용·라이브러리·신규 빈 프로젝트)**: 6번으로 건너뛴다.

판별 근거는 "라우트 정본(전문용어: 어떤 URL 이 어떤 코드로 연결되는지 적힌 원본 파일)이 있는가"다.
스택마다 다르다 — 라우터 등록 파일 한 곳에 모여 있을 수도, 코드 곳곳의 어노테이션/데코레이터일
수도, 설정 파일의 라우트 테이블일 수도 있다. **먼저 이 프로젝트의 정본이 무엇인지 확정하고 시작한다.**
정본을 못 찾으면 추측하지 말고 사용자에게 묻는다.

## 2. 전수 열거 (표본 추출 금지)

라우트 정본에서 엔드포인트를 **하나도 빠짐없이** 뽑는다. 총계를 센다.

- 열거 결과의 총계와 정본의 라우트 등록 수가 일치해야 한다. **숫자가 안 맞으면 명세가 아니다** —
  맞을 때까지 다시 센다.
- 공개 API·내부 전용·비-API(웹 페이지·정적 서빙·OAuth 콜백)를 구분해서 센다. 뒤 두 종류도
  총계에는 넣되 어느 도메인에도 안 들어가면 인덱스에만 목록으로 남긴다.
- 근거를 기록해 둔다: 정본 파일 경로 + 그때의 커밋 SHA(`git rev-parse --short HEAD`).

## 3. 도메인 분할

경로 프리픽스(`/api/v1/<이것>/...`)와 소유 모듈/컨트롤러를 묶어 도메인을 만든다.
한 도메인이 대략 40 엔드포인트를 넘으면 쪼갠다. 도메인 수가 3개 이하면 나누지 말고 하나로 둔다
(작은 프로젝트에 문서 7개는 과잉이다).

## 4. 공통 규약 실측

도메인 상세를 쓰기 전에 전 도메인이 공유하는 규약을 코드에서 확인한다:
성공 응답 형태(감싸는 껍데기가 있는지), 에러 형태와 HTTP status 관례, 인증 방식들(각각 언제 쓰이는지),
페이지네이션 방식, 다국어/버저닝 규약. **읽어서 추측하지 말고 실제 응답 생성 코드에서 확인한다.**

## 5. 기록 (도메인 → 인덱스 → 이력 순서)

`dw_write_reference(scope, title, body, source)` 로 기록한다. 순서를 지킨다 — 인덱스가 도메인
노트를 가리키므로 도메인이 먼저 있어야 링크가 안 끊긴다.

1. **도메인마다 하나씩**: title `API 명세 — <도메인 이름>`.
   각 엔드포인트에 대해: 메서드+경로 / 핸들러 위치 / 인증 / 요청 파라미터(위치·타입·필수 여부·기본값) /
   응답 shape / 에러 케이스. 문서 맨 위에 코드 경로와 실측 기준 커밋을 적는다.
2. **인덱스 하나**: title `API 명세 — 전체 인덱스`. 담을 것 —
   공통 규약(4번 결과) / 도메인별 엔드포인트 수와 상세 노트 파일명 표 / 총계 /
   어느 도메인에도 안 들어간 비-API 라우트 목록 / 실측 기준(정본 파일 @ 커밋 SHA) / 재대조 날짜.
3. **이력 하나**: title `API 명세 — 변경 이력`. 부트스트랩 항목 한 줄로 시작한다:
   `- **YYYY-MM-DD** · 부트스트랩 · 전 API 전수 스캔 — 총 N개(도메인 M개). 근거: <정본 경로> @ <SHA>`

`source` 인자에는 "전수 스캔 YYYY-MM-DD, <정본 경로> @ <SHA>" 를 넣는다.

## 6. 케이스 B — API 가 없을 때

**빈 인덱스와 빈 이력을 만든다.** 안 만들고 넘어가지 않는다 — "명세가 없다" 와 "명세가 비어 있다"
는 다르다. 후자여야 첫 API 를 만들 때 [[api-spec-update]] 가 갱신할 대상을 찾는다.

- 인덱스 body: "이 프로젝트는 현재 HTTP API 를 제공하지 않는다. 첫 엔드포인트가 생기면
  api-spec-update 절차로 이 문서를 채운다." + 공통 규약 자리(비워 두고 제목만).
- 이력 body: `- **YYYY-MM-DD** · 부트스트랩 · API 없음 — 빈 명세 생성.`
- 도메인 노트는 만들지 않는다.

## 7. 검증

- `dw_list(note_type="reference")` 에 인덱스·이력(+도메인들)이 보인다.
- 인덱스의 도메인별 합계 = 2번에서 센 총계. 다르면 틀린 것이다.
- 인덱스가 가리키는 도메인 노트 파일명이 실제 기록된 노트와 일치한다.

**주의:**
- 시간이 부족하다고 "주요 엔드포인트만" 담지 마라. 부분 명세는 없는 것보다 나쁘다 — 읽는 사람이
  전수라고 믿는다.
- 라우트 정본이 여러 개(멀티레포·서비스 분리)면 레포마다 이 절차를 따로 돌리고 인덱스도 따로 만든다.
  한 인덱스에 두 시스템을 섞지 않는다.
