API 를 건드리는 작업(엔드포인트 신설·변경·삭제, 그리고 그 API 를 **쓰는 쪽**의 연동)은
**vault 의 API 명세를 읽는 것으로 시작하고, 명세를 갱신하는 것으로 끝난다.**

## 읽기 범위 — 딱 이만큼만

전문을 다 읽으면 컨텍스트가 터진다. 세 줄이 전부다:

- **항상**: `API 명세 — 전체 인덱스` (`dw_read` 또는 `dw_search("API 명세 전체 인덱스")`).
  공통 규약(응답 형태·인증 방식·페이지네이션·에러)과 도메인 지도가 여기 있다.
- **필요할 때**: 지금 건드리는 **도메인 상세 노트 하나만**. 인덱스 표가 파일명을 알려준다.
- **표면을 바꾼 뒤**: `API 명세 — 변경 이력` 에 항목 추가.

인덱스가 없으면(`dw_search` 0건) 코드를 짜기 전에 api-spec-bootstrap 절차를 먼저 돌린다.

## 왜

- 이미 있는 엔드포인트를 모르고 또 만드는 일, 이미 있는 규약을 어기는 응답 형태를 새로 만드는 일이
  가장 흔한 API 사고다. 인덱스 한 번 읽으면 둘 다 막힌다.
- 명세는 **머지된 현재 상태**다. "앞으로 만들 것" 은 vault `contracts/` 의 몫이다 — 둘을 섞지 않는다.
  계약은 완결되면 archive 로 내려가고, 그 내용은 명세로 흡수된다.
- 명세와 코드가 어긋나면 **코드가 이긴다.** 명세를 코드에 맞춰 고치고 이력에 "변경" 으로 남긴다.
  추측으로 명세를 믿지 말고, 의심되면 라우트 정본을 직접 본다.

## 갱신은 언제

머지된 뒤다. 절차는 api-spec-update 를 따른다 — 도메인 노트 → 인덱스 카운트 → 이력 prepend 순서고,
이력은 반드시 `dw_read` 로 읽고 맨 위에 붙여 전체를 되돌려 쓴다(읽지 않고 쓰면 이력 전체가 날아간다).

대상이 아닌 변경: 내부 함수 시그니처, 리팩터링, 응답에 영향 없는 성능 개선. 판정 기준은
**호출하는 쪽이 관측할 수 있는 변화인가** 하나다.

durable 한 지식이 vault 로 가는 일반 규율은 [[artifact-locations]] 를 따른다.
