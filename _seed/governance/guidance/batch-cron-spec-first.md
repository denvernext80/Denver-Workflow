정기 실행 작업(배치=모아서 한 번에 처리, 크론=정해진 시각에 자동 실행)을 만들거나 바꾸거나 끄거나
지우는 작업은 **vault `배치·크론 명세 — 전체 인덱스` 를 읽는 것으로 시작하고, 명세 갱신으로 끝난다.**

읽기 범위·명세는 현재 상태·머지(적용) 후 갱신 같은 **공통 규율은 [[api-spec-first]] 와 같다.**
아래는 배치·크론에만 해당하는 차이점이다.

## 1. 정본이 레포 밖에도 있다

API 의 라우트 정본은 항상 레포 안이지만, 정기 실행은 절반이 호스트에 산다(호스트 크론 목록,
레포에 없는 타이머 유닛, 콘솔에만 있는 클라우드 스케줄러). 명세는 **레포 선언분과 호스트 설치분을
분리해 센다.**

호스트를 확인할 수 없으면(운영 접근이 상시 열려 있지 않은 게 정상이다) **`미확인 (최종 확인
YYYY-MM-DD, 사유)` 로 남긴다.** 확인하려고 보안 설정을 바꾸지 않는다.
**모른다고 적는 것이, 없다고 적는 것보다 정확하다** — 이 도메인 최대 사고는 틀린 명세가 아니라
아무도 모르는 채 도는 잡이다.

## 2. 드리프트 판정이 표면마다 다르다

- **레포 선언분** — 명세와 코드가 다르면 **코드가 이긴다.** 명세를 고치고 이력에 남긴다.
- **호스트 설치분** — 명세와 호스트가 다르면 **자동으로 명세를 맞추지 마라.** 누가 수동으로
  심었거나 지웠을 수 있고, 의도인지 사고인지는 사람만 안다. **불일치를 보고하고 판단을 받은 뒤**
  고친다. 조용히 맞추면 무단 변경이 정본으로 승격된다.

## 3. 꺼진 잡도 기록한다

`비활성`(꺼져 있음)은 `삭제`가 아니다. 상태 필드로 남기고 **왜 껐는지** 적는다 — 나중에 가장
자주 묻는 질문이다. 스케줄을 만질 땐 **타임존**을 함께 확인한다(서버 시간대와 표기 시간대가 다른
사고가 흔하다).

## 4. 적용 시점

명세에 반영하는 시점은 코드 머지가 아니라 **실제로 그 스케줄이 도는 상태가 된 때**(배포·설치 후)다.
선언만 하고 안 깔았으면 아직 현재 상태가 아니다. 절차는 batch-cron-spec-update 를 따른다.
인덱스가 없으면 batch-cron-spec-bootstrap 을 먼저 돌린다.
